# Замена `core/screener.py`: что изменено и почему

Дата: 2026-07-31. Основа — присланная рабочая версия скринера (порт из Lovable-проекта scalp-buddy).
Решения, зафиксированные владельцем: данные с WS Bybit mainnet при ордерах на Testnet; отбор на NATR-14 + UHLO с добавленной верхней границей.

**Перенесено без изменений**: `compute_natr`, `compute_uhlo`, `classify_color`. Индикаторы проверены на живом потоке, и порядок индексов `k[2]/k[3]/k[4]` одинаков у Binance и Bybit v5, поэтому переписывать их не потребовалось.

## Блокеры цели этапа

| # | Было | Стало | Почему |
|---|------|-------|--------|
| 1 | Данные с `fapi.binance.com`, ордера на Bybit Testnet | WS `stream.bybit.com/v5/public/linear`, ордера остаются на Testnet | Цена сигнала и цена исполнения приходили с разных бирж, и «проскальзывание» в журнале было межбиржевым базисом. Калибровать по нему 0.3–0.5% нельзя |
| 2 | В payload нет цены и метки времени | `price`, `price_venue`, `ts`, `signal_id` + диагностика | Обе метрики этапа из прежнего сигнала не вычислялись; задержка мерилась от POST и выглядела бы в миллисекундах |
| 3 | REST-опрос: `scan_interval_sec=120` + последовательный обход кандидатов | Событийная обработка на закрытии минутной свечи | Реальный возраст сигнала к моменту ордера — десятки секунд. Метрика была бы зелёной, а вывод ложным |
| 4 | Символ проверялся на наличие в списке **Binance** | Вселенная = пересечение инструментов mainnet **и Testnet** | Ордер уходит на Bybit; контракты с множителем (`1000…`) называются на биржах по-разному. Отклонённый ордер нарушал SC-002 |

## Добавлено сверх разбора

- **Перечитывание истории после обрыва** (`reseed_after_sec`, 90 с). После разрыва в окне свечей остаётся дыра, а `push()` отбрасывает всё старше последней свечи — доклейка молча оставила бы разрывную историю, по которой NATR и UHLO неверны. Окно заменяется целиком, подписка оформляется до чтения REST, чтобы не потерять свечи, закрывшиеся во время запроса.
- **Сторож тишины** (`ws_stale_sec`). На Android после сна соединение часто остаётся открытым, но данные не идут; без сторожа скринер молча слепнет, а прогон выглядит успешным.
- **Проверка расхождения часов** по обоим контурам: по mainnet скринер ставит метки сигналов, по Testnet бот подписывает ордера.
- **Интервалы недоступности потока** в журнале (`stream_down` / `stream_up`) — чтобы сигналы, которые могли возникнуть в «слепом» окне, не считались пропущенными.
- **Логирование исключений в фоновых задачах**: без `add_done_callback` ошибка обработки свечи уходила бы в «Task exception was never retrieved».
- **Отбор причин для журнала** (`reject_log`). 300 символов × 1440 минут — миллионы строк за 72 часа. В режиме `candidates` шум (`insufficient_history`, `natr_below_min`, `repeat_color`) не пишется, а `natr_above_max` пишется всегда: он и есть доказательство SC-006. Оценка объёма ~40 МБ за прогон.

## Контракт с ботом

Сигнал (`POST /signal`):

```json
{
  "source": "local_screener",
  "signal_id": "BTCUSDT:1:1753960800000",
  "symbol": "BTCUSDT",
  "side": "Buy",
  "mode": "DCA",
  "price": 68142.5,
  "price_venue": "bybit_mainnet",
  "ts": 1753960860123,
  "diagnostics": {
    "natr": 1.42,
    "uhlo_1m": {"highs": 0.0, "lows": 100.0},
    "uhlo_15m": {"highs": 5.0, "lows": 95.0},
    "color": "green",
    "candle_start": 1753960800000,
    "detection_lag_ms": 123
  }
}
```

Что должен сделать бот на своей стороне:

1. Отсечь дубликат по `signal_id` и по открытому циклу; использовать `signal_id` как основу `orderLinkId` для идемпотентности.
2. В момент получения записать **свою** последнюю известную цену Testnet — без неё проскальзывание неотделимо от базиса контуров (FR-020a).
3. Взять параметры DCA и плечо из своего конфига, а не из сигнала.
4. Проверить `minOrderQty`, `qtyStep`, `tickSize`, `maxLeverage` перед выставлением ордера.
5. Считать задержку от `ts`, а не от момента получения HTTP-запроса.
6. Проверить расхождение часов с **Testnet** перед началом торговли.

## Сводка по прогону

`reference/report.py` читает журналы обоих процессов и выдаёт медиану и p95 задержки и проскальзывания, базис между контурами отдельной величиной, счётчики сигналов по статусам, циклы по причине выхода, интервалы недоступности и вердикт по каждому измеримому критерию приёмки. Зависимостей нет — считается на том же устройстве, где шёл прогон.

```bash
python3 tools/report.py logs/screener-events.jsonl logs/bot-events.jsonl
python3 tools/report.py 'logs/*.jsonl' --json --since 2026-08-01T00:00:00
```

Критерии, которые из журнала не проверяются (SC-006, SC-008, SC-011), помечаются как требующие ручной проверки, а не выполненными: сводка не должна выглядеть полнее, чем есть. Точный перечень ожидаемых записей — в docstring `report.py`, он же и есть контракт для бота.

Заодно поправлено в `Journal.write`: `kind` и `ts` выставляются после остальных полей. Раньше `ts` из payload сигнала молча перезаписывал журнальную метку времени, и строка теряла момент записи.

## Метки времени цикла, сводка и healthcheck (2026-08-07)

Три добавки к рабочей копии `~/bybit-dca-bot` (зеркало — этот репозиторий).

### 1. Точное время начала и окончания цикла в структурированный журнал

`core/main_bot.py` и `core/monitor.py` теперь пишут в `logs/bot-events.jsonl`
(ключ `bot.journal_path`) явные метки, а не только строки в `bot.log`:

- `cycle_opened` → добавлено поле `open_ts` (epoch-мс начала цикла);
- `cycle_recovered` → добавлено поле `open_ts` (из `createdTime` позиции);
- `cycle_closed` → добавлены `open_ts`, `close_ts` и `duration_ms`
  (`close_ts − open_ts`), `held_sec` сохранён для обратной совместимости.

Пример закрытия (TP/SL/time_exit/manual — все пути идут через
`Monitor._handle_vanished`):

```json
{"kind":"cycle_closed","cycle_id":"C1","symbol":"BTCUSDT","exit_reason":"take_profit",
 "pnl":0.64,"open_ts":1753960860123,"close_ts":1753961400000,
 "duration_ms":539877,"held_sec":539,"ts":1753961400000}
```

### 2. `tools/stats_summary.py` — сводка по закрытым циклам

Читает `logs/bot-events.jsonl` и печатает: сколько циклов закрыто, разбивку по
причине (TP / SL / time_exit / manual), совокупный PnL в USDT, win-rate
(прибыльный = pnl > 0, как в `tools/backtest.py`), среднюю/медианную/min/max
длительность удержания и (опционально) разбивку по символам. Период фильтруется
по моменту закрытия.

```bash
python3 tools/stats_summary.py                        # всё время
python3 tools/stats_summary.py --days 7               # последние 7 суток
python3 tools/stats_summary.py --days 7 --by-symbol   # + по символам
python3 tools/stats_summary.py --json                 # машиночитаемо
```

Старые записи без полей `open_ts/close_ts/duration_ms` тоже разбираются: моменты
берутся из `ts` событий, цикл связывается с `cycle_opened` по `cycle_id`.
События с `pnl: null` учитываются в счётчиках, но не в PnL и win-rate (их число
выводится как «циклов_с_pnl»).

### 3. `tools/healthcheck.sh` — проверка живости бота

Дёргает `http://localhost:8000/health`, пишет строку с timestamp в
`logs/healthcheck.log` (по умолчанию `<бот>/logs/`, переопределяется через
`HEALTHCHECK_LOG`). Провал помечается явным `FAIL` и возвращает ненулевой код
выхода (код `curl`), чтобы его было легко поймать и найти в логе. Режимы:

```bash
tools/healthcheck.sh                                # разовый запуск
tools/healthcheck.sh --daemon-interval 300          # фоновый цикл (фоллбэк без cron)
```

Периодический запуск в Termux:
- **termux-job-scheduler** (`pkg install termux-api`):
  `termux-job-scheduler --script "$HOME/bybit-dca-bot/tools/healthcheck.sh" --interval-ms 300000 --persisted true`;
- **cron** (`pkg install cronie termux-services`, затем `sv-enable crond`, `crontab -e`
  → `*/5 * * * * ~/bybit-dca-bot/tools/healthcheck.sh`);
- **демон-цикл** без зависимостей: `nohup ... healthcheck.sh --daemon-interval 300 &`.

В любом варианте держать Termux под `termux-wake-lock`, иначе Android усыпит
устройство и проверка вместе с ботом не будут выполняться.

Автопроверки: `reference/test_cycle_journal.py` (17) и `reference/test_stats_summary.py`

## Фантомный `cycle_closed` при неисполнившемся закрытии (2026-08-08)

На тестнете найден позиция, которую невозможно закрыть: у символа
`1000RATSUSDT` полностью пустой стакан (пустой orderbook, `turnover24h=0`,
маркет-ордера отменяются биржей за ~3 мс). Бот при этом вёл себя неправильно:

- на каждом рестарте позиция восстанавливалась, `max_hold_hours` был давно
  превышен → `close_cycle` отправлял закрывающий маркет-ордер;
- ордер отменялся (нечего матчить), а `close_cycle` всё равно вызывал
  `_handle_vanished` и снимал цикл — журнал получал **ложный** `cycle_closed`
  с `pnl: null`;
- при следующем рестарте позиция всплывала снова, и так по кругу (позиция
  «закрывается» каждый запуск, но ни разу не закрывается по факту).

Исправление в `core/monitor.py` (рабочая копия `~/bybit-dca-bot`):

- `close_cycle` считает закрытие успешным только при исполнении (филл) **или**
  подтверждённом отсутствии позиции на бирже (`_confirm_gone` — повторный
  запрос `positions(symbol)`; обрыв сети трактуется как «не закрыта», чтобы не
  снимать цикл по неясному статусу);
- ни один ордер не исполнился и позиция на месте → цикл **не снимается**,
  в журнал пишется `close_failed` (после `close_retry_max_attempts` попыток —
  `close_stuck`), повторные попытки с экспоненциальной паузой 5..120 с, далее
  10 минут; такой же backoff применяется при ошибке размещения ордера;
- очистка счётчиков попыток — в `_handle_vanished`.

Журнальные записи: `close_failed {symbol, reason, attempts, retry_after_sec}` и
`close_stuck` (те же поля) — `tools/report.py` их игнорирует как незнакомые
`kind`, сводка не ломается. Тесты: `tests/test_bot.py` (+3 проверки) — закрытие
по пустому стакану оставляет цикл и пишет `close_failed`, backoff-пауза не шлёт
повторный ордер, после истечения паузы попытка повторяется, задержавшееся
подтверждение закрытия снимает цикл с причиной `time_exit`. Итог: 213 ok, 0 fail.

Наблюдение для прогона: `1000RATSUSDT` на тестнете не закрыть никаким ордером
(пустой стакан). Для тестового счёта это безвредно (~76 USDT виртуальных,
unrealised ≈ −5 USDT), но такие позиции нужно исключать из вселенной до того,
как они появятся, или закрывать вручную в UI. У биржевого тейка на такой
позиции та же судьба — не сработает без сделок.

## Трейлинг-тейк-профит (2026-08-07)

Новые параметры `dca.trail_trigger_pct` (порог активации, % прибыли от средней
цены входа; `0` — выключен) и `dca.trail_step_pct` (откат от пика цены, %).
Когда прибыль достигает порога, монитор включает трейлинг: уровень выхода
тащится за пиком цены и закрывает цикл при откате на `trail_step_pct` от пика
(причина выхода `trailing`). Обычный `take_profit_pct` остаётся фолбэком — если
пик не поднялся выше него, срабатывает обычный тейк.

Реализация (рабочая копия `~/bybit-dca-bot`):

- `core/dca_strategy.py`: поля `trail_trigger_pct`/`trail_step_pct` в `DcaParams`,
  чтение из конфига, помощник `trail_exit_price` (уровень выхода от пика: для
  лонга ниже пика, для шорта выше).
- `core/main_bot.py`: состояние трейлинга в `Cycle` (`peak_price`,
  `trail_active`, `trail_level`), пик инициализируется ценой входа; поля в
  `status()` (`trail_active`, `trail_peak`, `trail_level`) и в `bot_started`.
- `core/monitor.py`: проверка трейлинга в `_check_cycle` между тейк-профитом и
  докупкой; активация пишет событие `trail_activated`; при росте пика биржевой
  тейк переносится за уровень выхода (`refresh_take_profit(symbol, trail_level)`),
  чтобы после смерти процесса позиция всё равно закрылась по трейлингу; докупка
  сбрасывает состояние трейлинга (средняя сместилась, пик устарел); исчезновение
  позиции при активном трейлинге без нашей команды трактуется как выход
  `trailing` (на бирже стоит именно его уровень, а не обычный тейк).

Причины выхода: `cycle_closed.exit_reason` дополнена значением `trailing`;
`tools/stats_summary.py` разбирает его отдельной строкой «по трейлингу».

Поведение: трейлинг проверяется раньше докупки — после активации откат закрывает
цикл, а не ведёт к усреднению. В худшем случае трейлинг оставляет прибыль
`trail_trigger_pct − trail_step_pct` выше средней. Тесты: `tests/test_bot.py`
(активация, подтягивание уровня за пиком, закрытие по откату, шорт, порог 0,
поля статуса).

## Защита от входа в LONG на хае памп-бара (2026-08-08)

Скринер не учитывал объём: если закрытая свеча 1м — локальный хай с длинной
верхней тенью и объёмом в разы выше среднего (памп), `evaluate` возвращал
зелёный сигнал как обычно, и вход в лонг приходился на откат от хая.

Исправление в `core/screener.py` (рабочая копия `~/bybit-dca-bot`):

- строки свечей получили объём: REST `fetch_klines` — `r[5]`, WebSocket
  `_on_message` — `item["volume"]`; формат `[ts, open, high, low, close, volume]`;
- для LONG (`green`) после цветовой классификации последняя ЗАКРЫТАЯ свеча
  проверяется функцией `pump_bar(fast, cfg)`: объём выше
  `pump_volume_mult` × среднего объёма за предыдущие 20 свечей **и** верхняя
  тень (`high − max(open, close)`) длиннее `pump_wick_ratio` × размаха бара →
  `reason: pump_bar`, сигнал подавляется (журналируется, как и `natr_above_max`);
- SHORT защита не касается: на красном памп-баре с длинной тенью цена уже
  откатила вниз, и шорт в неё входить можно;
- окно скринера хранит `uhlo_length*2+4` свечей (при `uhlo_length=20` — 44),
  среза `fast[-21:]` для среднего объёма достаточно;
- параметры в секции `screener`: `pump_volume_mult: 3.0`, `pump_wick_ratio: 0.5`
  (0 — проверка выключена; `pump_bar` выходит сразу при `mult <= 0`).

Строки без объёма (старые окна, тесты) трактуются как нулевой объём → проверка
молча не срабатывает, существующие сигналы не меняются. Тесты:
`tests/test_screener.py` (+7 проверок) — памп-бар с длинной тенью подавляет
лонг, тень без объёма и объём без тени сигнал оставляют, `pump_volume_mult=0`
выключает защиту, красный памп-бар шорт не подавляет. Итог: 78 ok, 0 fail.

## Шорт только на неперепроданном рынке (2026-08-08)

Красный сигнал (SHORT) уходил и на «свежем дампе», когда UHLO `highs` 1м
прижаты к 100: цена уже свалилась от всех хаёв окна, и вход в шорт приходился
на опоздавшую цену. Правило «разрешать SHORT только если рынок не перепродан»
отображается на UHLO так (spec.md FR-004, осциллятор проекта — Unreached
Highs/Lows):

- красный сигнал и так требует `highs` 1м и 15м в 80..100 и `lows` в 0..20,
  поэтому буквальный порог «> 25» был бы либо пустышкой (по `highs`),
  либо запретил бы все шорты (по `lows`, в красном `lows ≤ 20`);
- вместо этого сужена верхняя граница полосы красного по 1м: в `evaluate`
  для `red` проверяется `uhlo_fast["highs"] > short_highs_max` → сигнал
  подавляется с `reason: short_oversold` (детали: `highs_1m`, `highs_max`);
- параметр `screener.short_highs_max: 90.0` (полоса красного 80..90; свежий
  дамп не шортится; 100 — проверка выключена). LONG не затронут;
- состояние цвета: отклонённый `short_oversold` цвет не фиксирует (сброс
  `last_color` идёт только у `uhlo_no_color`/`uhlo_slow_missing`), так что
  после «перепроданного» окна нормальный красный сигнал не теряется.

Тесты: `tests/test_screener.py` (+5 проверок) — фикстура с мягким
восстановлением в хвосте даунтренда (highs 1м 85) шорт пропускает, чистый даун
(highs 100) даёт `short_oversold`, `short_highs_max=100` выключает проверку,
детали журналируются; pump-тест SHORT-ветки переведён на `short_highs_max=100`,
чтобы проверять независимо. Итог: 83 ok, 0 fail.

## Адаптивные шаг сетки и стоп от ATR-14 (2026-08-08)

## Dynamic SL, кулдаун после стоп-выхода и 15m Safety-фильтр доливок (2026-08-08)

Три добавки к рабочей копии `~/bybit-dca-bot` (зеркало — этот репозиторий).
Все параметры — в секции `dca` конфига, `0`/выключение восстанавливает прежнее
поведение.

### 1. Dynamic SL для Level 2 (аварийный стоп по обновлённой средней)

После выполнения `dynamic_sl_level` докупок (по умолчанию 2 — Level 2) стоп
цикла пересчитывается с обычного `hard_sl_pct` на тугой `dynamic_sl_pct`
(1.3%) **от обновлённой средней цены позиции** — на каждом такте монитора.
Смысл: после второй доливки лестница уже раздула номинал Мартингейлом, и
растянутый стоп `hard_sl_pct` оставил бы крупный убыток, если тренд против
позиции продолжается; тугой стоп отсекает глубокие лестницы раньше.

Реализация (рабочая копия `~/bybit-dca-bot`):

- `core/dca_strategy.py`: поля `DcaParams.dynamic_sl_level` / `dynamic_sl_pct`,
  чтение из конфига;
- `core/main_bot.py`: `Cycle.dynamic_sl_pct` (None до активации);
  `effective_hard_sl()` возвращает динамический стоп, если он активирован —
  этим живут и проверка стопа в мониторе, и вывод `status()`;
- `core/monitor.py`: после исполнения доливки с номером ≥ `dynamic_sl_level`
  цикл получает `dynamic_sl_pct` (один раз), пишется событие
  `dynamic_sl_activated {cycle_id, symbol, step, avg_price, sl_pct}`; сработавший
  стоп закрывает цикл с причиной `dynamic_sl` (а не `hard_sl`) — отдельно в
  журнале и в разбивке `stats_summary.py`.

Причина выхода: `cycle_closed.exit_reason` дополнена значением `dynamic_sl`.

### 2. Кулдаун монеты после стоп-выхода

Параметр `sl_cooldown_hours` (по умолчанию 2): если цикл закрылся по `hard_sl`
или `dynamic_sl`, монета на `sl_cooldown_hours` часов НЕ принимает новые входы.
Монета, только что выбившая стоп, с высокой вероятностью продолжит движение
против позиции; немедленный повторный вход — удвоенный риск без новой
информации.

Реализация (рабочая копия `~/bybit-dca-bot`):

- `core/main_bot.py`: `DcaBot.sl_cooldowns` (`symbol -> until_ms`); `_open_cycle`
  отклоняет сигнал со статусом `cooldown` и причиной «активен кулдаун после
  стоп-выхода: осталось ~N мин»; поле `cooldowns` в `status()`/`/health`
  (`until_ms` + `left_sec`);
- `core/monitor.py`: `_set_cooldown(symbol)` вызывается из `close_cycle` при
  причине `hard_sl` / `dynamic_sl`, пишет событие
  `cooldown_set {symbol, hours, until_ms}`.

Тейк-профит и выход по времени кулдаун не ставят: только стоп-выходы.

### 3. Safety-фильтр доливок по объёму 15m

Перед исполнением доливки уровня `safety_level` и выше (по умолчанию 2) монитор
проверяет **последнюю закрытую свечу** таймфрейма `safety_interval` (15м). Если
свеча движется ПРОТИВ позиции (для лонга медвежья `close < open`, для шорта
бычья `close > open`) **и** её объём выше `safety_volume_mult` × среднего объёма
за `safety_lookback` предыдущих свечей — доливка блокируется, а цикл переводится
в режим ожидания `safety_hold`: усреднение не возобновляется, позиция ждёт TP
или SL. Цель — не подливать под аномальный распродажный объём.

Реализация (рабочая копия `~/bybit-dca-bot`):

- `core/dca_strategy.py`: поля `DcaParams` — `safety_level`, `safety_interval`,
  `safety_volume_mult`, `safety_lookback`;
- `core/api_client.py`: `BybitClient.klines(symbol, interval, limit)` — закрытые
  свечи текущего контура для фильтра; ошибка/отсутствие данных возвращают `[]`,
  монитор не падает;
- `core/main_bot.py`: `Cycle.safety_hold`; поле в `status()`/`/health`;
- `core/monitor.py`: `_safety_volume_blocked(symbol, side)` — фильтр выше; при
  блокировке пишется событие `dca_blocked {symbol, step, side,
  reason: safety_volume_15m, interval, volume_mult}`, ставится `safety_hold`
  (докупка запрещена тем же условием, что и Smart Timeout);
- **Fail-open**: ошибка биржи или пустой ответ `klines` → доливка разрешена
  (False), фильтр не должен останавливать лестницу из-за недоступности данных.

Поведение шорта симметрично: аномальный бычий объём блокирует усреднение шорта.

## Поуровневый тейк-профит (эскалация TP от бэктеста) (2026-08-08)

TP растёт с глубиной лестницы: каждая доливка усредняет позицию дальше от цены
сигнала, и для отработки разросшегося Мартингейлом номинала нужно большее
расстояние до выхода. Уровень = число выполненных докупок (`cycle.dca_done`).

| Уровень | Число докупок | TP |
|---------|---------------|-----|
| Level 0 | вход без доливок | 1.2% |
| Level 1 | после 1-й доливки | 1.5% |
| Level 2 | после 2-й доливки | 2.0% |

`SL_TIGHT_LEVEL = 2` (Dynamic SL 1.3% строго со 2-й доливки) оставлен без
изменений: `dca.dynamic_sl_level: 2`, `dca.dynamic_sl_pct: 1.3`.

- `core/dca_strategy.py`: константы `TP_PCT_0/1/2` (1.2/1.5/2.0) и
  `SL_TIGHT_LEVEL`/`SL_TIGHT_PCT`; поле `DcaParams.tp_escalation: list[float]`;
  чистая функция `take_profit_pct_at(params, level)` — уровень N возвращает
  элемент эскалации, выше последнего удерживается максимум, пустой список —
  фиксированный `take_profit_pct` (прежнее поведение).
- `core/main_bot.py`: `Cycle.take_profit_at()` и `cycle_opened` в журнале
  используют уровень `dca_done` (на входе — Level 0). Параметр и текст старта
  логируются (поуровневый TP `1.20% → 1.50% → 2.00%`).
- `core/monitor.py`: и фолбэк-закрытие по TP (шаг 2.5), и перенос биржевого
